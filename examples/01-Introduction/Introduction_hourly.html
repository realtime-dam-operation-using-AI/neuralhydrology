Introduction to NeuralHydrology — 시간(hourly) 단위 버전¶

시작하기 전에

  • 이 노트북은 공식 튜토리얼 examples/01-Introduction/Introduction.ipynb를 그대로 따라가되, 일(daily) 단위가 아니라 시간(hourly) 단위 자료만으로 같은 실험을 돌려본 버전입니다. 설정 파일은 같은 폴더의 1_basin_hourly.yml입니다.
  • 실행하려면 CAMELS US 자료 중 hourly 부분이 필요합니다. 저장소 루트 기준 data/CAMELS_US/hourly/ 아래에 두 개의 폴더가 있어야 합니다.
    • nldas_hourly/ — <basin>_hourly_nldas.csv (시간 단위 기상 강제자료)
    • usgs_streamflow/ — <basin>-usgs-hourly.csv (시간 단위 관측 유량)
    • 내려받는 방법은 examples/00-Data-Prerequisites/prerequisites.ipynb의 "Hourly forcing and streamflow data for CAMELS US basins" 절을 참고하세요.
  • 설치 방법은 Quickstart 문서를 참고하세요.
  • 기본 설정은 CUDA GPU를 가정합니다. GPU가 없으면 device: cpu로 바꾸거나 start_run()에 gpu=-1을 넘기세요.

왜 hourly인가¶

Introduction.ipynb는 daymet/maurer/nldas의 일 평균 강제자료로 하루 1개의 유량(QObs(mm/d))을 예측합니다. 이 방식은 장기 물수지나 갈수기 거동을 보기에는 충분하지만, 홍수 예보 관점에서는 두 가지가 아쉽습니다.

  1. 첨두 유량의 발생 시각을 알 수 없습니다 — 하루 평균으로 뭉개지면 오전 첨두와 오후 첨두의 구분이 사라집니다.
  2. 작은 유역일수록 집중시간(time of concentration)이 몇 시간 단위라, 하루 해상도로는 강우–유출 반응 자체가 한 스텝 안에서 끝나버립니다.

시간 단위 자료를 쓰면 같은 LSTM 구조로 위 두 가지를 그대로 살릴 수 있습니다. NeuralHydrology에서는 모델 코드를 전혀 바꾸지 않고 config만 바꿔서 이걸 할 수 있습니다 — dataset: hourly_camels_us가 그 역할을 합니다.

daily 설정에서 무엇이 바뀌는가¶

검증/테스트 기간이 바뀐 이유는 데이터가 없기 때문입니다 — 시간 단위 USGS 유량은 1989-10-01부터 시작하므로 daily 튜토리얼의 1980~1989 검증 기간을 쓸 수 없습니다. 그래서 examples/04-Multi-Timescale/1_basin.yml과 같은 분할(train 1999–2008 / validation 1996–1999 / test 1989–1996)을 사용합니다.

seq_length는 "며칠치 과거를 보는가"를 기준으로 맞췄습니다. daily 365스텝은 1년이지만, hourly에서 365스텝은 15일밖에 안 됩니다. 이 튜토리얼에서는 30일, 즉 1개월(720스텝) 을 씁니다.

1개월을 고른 이유:

  • 선행 습윤 상태(antecedent wetness)를 담기 위해서입니다. 같은 양의 비가 내려도 지난 몇 주가 습했는지 건조했는지에 따라 유출량이 크게 달라지는데, 그 "기억"의 시간 규모가 대략 몇 주~한 달입니다. 7일(168스텝)로는 토양 수분 상태의 상당 부분이 시퀀스 밖으로 밀려납니다.
  • 1년치(8,760스텝)를 통째로 넣으면 학습이 비현실적으로 느려집니다. 720은 "선행 습윤 상태는 담되 계산은 감당 가능한" 절충점입니다.
  • models_nbs/의 모든 hourly 노트북이 같은 값을 써서 모델 간 비교가 공정해집니다.

비용도 정직하게 적어두면: ARLSTM, CustomLSTM, EA-LSTM, MC-LSTM, HybridModel은 타임스텝마다 파이썬 루프를 돌기 때문에 720은 168보다 약 4배 느립니다. 이 노트북들의 학습 시간이 다른 노트북보다 훨씬 긴 이유입니다.

examples/04-Multi-Timescale/1_basin.yml과 test/test_configs/multi_timescale_regression.test.yml은 타깃을 qobs_mm_per_hour로 씁니다. 그 이름은 전처리된 NetCDF 파일(hourly/usgs-streamflow-nldas_hourly.nc)의 변수명입니다. 이 저장소의 data/CAMELS_US/hourly/에는 NetCDF가 없어서 HourlyCamelsUS.load_hourly_data()가 CSV fallback 경로를 타고(## Warning: Hourly nldas_hourly NetCDF file not found. 경고가 찍힙니다), 그때 컬럼명은 CSV 원본 그대로인 QObs(mm/h)가 됩니다.

early stopping을 켤 때 같이 알아둘 점 (라이브러리 동작)¶

neuralhydrology/utils/config.py를 보면:

  • early_stopping: True는 validate_every: 1을 강제합니다 (아니면 ValueError).
  • Config.dynamic_learning_rate가 early_stopping 값을 그대로 돌려주도록 구현되어 있어서, early stopping을 켜면 ReduceLROnPlateau도 자동으로 같이 켜집니다. 그래서 patience_dynamic_learning_rate / factor_dynamic_learning_rate를 반드시 지정해야 하고, config의 learning_rate: 딕셔너리에 적은 epoch별 수동 스케줄은 무시됩니다(basetrainer.py의 if not self._dynamic_learning_rate: 가드). learning_rate: {0: 1e-3}의 0번 항목만 optimizer 초기 학습률로 쓰입니다.
  • early stopping은 검증 loss가 좋아지지 않으면 학습을 멈출 뿐, 가장 좋았던 가중치로 되돌려주지는 않습니다. 그래서 아래에서 output.log를 파싱해 검증 loss가 최소였던 epoch을 직접 찾아 그 체크포인트로 평가합니다.

이 노트북이 쓰는 보조 함수¶

models_nbs/의 모든 *_hourly.ipynb가 공유하는 네 개의 보조 함수입니다. 폴더당 파일 수를 늘리지 않으려고 별도 모듈로 빼지 않고 각 노트북에 그대로 인라인해 두었습니다.

  • latest_run_dir(name) — run 디렉터리 이름에는 실행 시각이 붙으므로, 가장 최근 것을 자동으로 찾습니다 (튜토리얼에 타임스탬프를 하드코딩하지 않기 위해).
  • validation_history(run_dir) — output.log에서 epoch별 검증 loss/metric을 파싱합니다.
  • best_epoch(run_dir) — 검증 loss가 최소였던 epoch. early stopping은 가장 좋았던 가중치로 되돌려주지 않으므로, 평가는 마지막 epoch이 아니라 이 epoch의 체크포인트로 해야 합니다.
  • completed_run_dir(name) — 이미 학습이 끝난 run이 있는지 확인합니다. 아래 학습 셀이 이걸 보고 재학습을 건너뜁니다.
  • reset_logging() — 한 커널에서 start_run()을 두 번 이상 부르기 전에 필요합니다 (아래 docstring 참고).

def latest_run_dir(experiment_name: str, runs_dir: Path = Path("runs")) -> Path:
    """실행할 때마다 날짜/시간이 폴더명에 붙으므로, 가장 최근 run 디렉터리를 자동으로 찾는다."""
    candidates = sorted(runs_dir.glob(f"{experiment_name}_*"), key=lambda p: p.stat().st_mtime)
    if not candidates:
        raise FileNotFoundError(f"'{experiment_name}'으로 시작하는 run 디렉터리가 {runs_dir} 아래에 없습니다.")
    return candidates[-1]


def validation_history(run_dir: Path) -> pd.DataFrame:
    """output.log에서 epoch별 검증 loss와 검증 metric을 파싱한다."""
    line_re = re.compile(r"Epoch (\d+) average validation loss: ([0-9.]+)(.*)")
    metric_re = re.compile(r"(\w[\w\-]*): (-?[0-9.]+)")
    rows = []
    for match in line_re.finditer((run_dir / "output.log").read_text()):
        row = {"epoch": int(match.group(1)), "val_loss": float(match.group(2))}
        row.update({k: float(v) for k, v in metric_re.findall(match.group(3)) if k != "avg_loss"})
        rows.append(row)
    if not rows:
        raise RuntimeError(f"{run_dir / 'output.log'}에서 검증 기록을 찾지 못했습니다.")
    return pd.DataFrame(rows).set_index("epoch")


def best_epoch(run_dir: Path) -> int:
    """검증 loss가 최소였던 epoch = early stopping이 되돌아갈 '최고 성능' 지점."""
    return int(validation_history(run_dir)["val_loss"].idxmin())


def completed_run_dir(experiment_name: str, runs_dir: Path = Path("runs")) -> Path | None:
    """학습이 이미 끝난 run이 있으면 그 디렉터리를, 없으면 None을 돌려준다.

    노트북을 다시 실행할 때마다 몇 시간씩 재학습하지 않기 위한 가드입니다.
    '끝난 run'의 기준은 (1) 체크포인트가 하나 이상 있고 (2) output.log에 검증 기록이 있는 것입니다.
    """
    if not runs_dir.is_dir():
        return None
    candidates = sorted(runs_dir.glob(f"{experiment_name}_*"), key=lambda p: p.stat().st_mtime, reverse=True)
    for candidate in candidates:
        if not list(candidate.glob("model_epoch*.pt")):
            continue
        try:
            if validation_history(candidate).empty:
                continue
        except (RuntimeError, FileNotFoundError):
            continue
        return candidate
    return None


def reset_logging() -> None:
    """같은 커널에서 start_run()을 두 번 이상 부르기 전에 호출해야 하는 함수.

    neuralhydrology의 setup_logging()은 logging.basicConfig(handlers=[...])를 쓰는데,
    root logger에 이미 핸들러가 붙어 있으면 basicConfig는 조용히 아무 일도 하지 않습니다.
    그래서 두 번째 run의 output.log는 '빈 파일'이 되고, 로그는 첫 번째 run의 파일로 계속 흘러갑니다
    (models_nbs/customlstm/runs/cudalstm_equivalent_run_*/output.log가 비어 있는 것이 그 실제 사례).
    아래처럼 핸들러를 먼저 떼어내면 두 번째 run도 자기 output.log를 정상적으로 씁니다.
    """
    import logging

    for handler in logging.root.handlers[:]:
        logging.root.removeHandler(handler)
        handler.close()

어떤 epoch을 평가할 것인가 — early stopping과 "최고 성능"¶

epochs: 100은 상한이고, 실제 종료 시점은 early stopping(patience_early_stopping: 10)이 결정합니다. 다만 early stopping은 학습을 멈출 뿐, 가장 좋았던 가중치로 되돌려주지 않습니다(neuralhydrology/training/basetrainer.py의 break 참고). 마지막 epoch은 정의상 "10 epoch 동안 나빠지기만 한" 지점입니다.

그래서 save_weights_every: 1로 매 epoch 체크포인트를 남겨두고, output.log에서 검증 loss가 최소였던 epoch을 찾아 그 체크포인트로 테스트 평가를 합니다 (위에서 정의한 best_epoch()).

hourly만의 관찰 포인트¶
1. NSE를 daily와 직접 비교하면 안 된다¶
Introduction.ipynb(daily)의 NSE와 이 노트북(hourly)의 NSE는 분모가 다릅니다. NSE의 분모는 관측치의 분산인데, 시간 단위 유량은 일 평균 유량보다 분산이 훨씬 큽니다(첨두가 평균화되지 않으므로). 그래서 같은 모델이라도 hourly NSE가 daily NSE보다 낮게 나오는 것이 정상입니다. 아래에서 같은 예측을 일 단위로 집계해서 daily 기준 NSE를 계산해보면 이 점이 분명해집니다.

2. 첨두 시각 오차 (timing error)¶
hourly 모델에서만 물어볼 수 있는 질문입니다 — "모델이 예측한 첨두가 관측 첨두보다 몇 시간 이르거나 늦었는가?" 테스트 기간에서 관측 유량 상위 홍수 사건들을 뽑아 첨두 시각 차이를 계산해봅니다.


















In [13]:






obs_series = qobs.to_series()
sim_series = qsim.to_series()

# 관측 유량 상위 20개 시점을 서로 72시간 이상 떨어지도록 골라 '독립 홍수 사건'으로 본다
events, candidates = [], obs_series.sort_values(ascending=False)
for timestamp in candidates.index:
    if all(abs((timestamp - e).total_seconds()) > 72 * 3600 for e in events):
        events.append(timestamp)
    if len(events) == 20:
        break

lags = []
for peak in sorted(events):
    window = slice(peak - pd.Timedelta("24h"), peak + pd.Timedelta("24h"))
    sim_window = sim_series.loc[window]
    if sim_window.isna().all():
        continue
    lags.append((sim_window.idxmax() - peak).total_seconds() / 3600)

lags = pd.Series(lags, name="첨두 시각 오차 (시간, +면 예측이 늦음)")
print(lags.describe().round(2))
print()
print(f"첨두 시각을 ±3시간 안에 맞춘 비율: {(lags.abs() <= 3).mean():.0%}")

fig, ax = plt.subplots(figsize=(8, 4))
ax.hist(lags, bins=np.arange(-24.5, 25.5, 3))
ax.axvline(0, color="crimson", ls="--")
ax.set_xlabel("simulated peak - observed peak (hours)")
ax.set_ylabel("사건 수")
ax.set_title("상위 홍수 사건의 첨두 시각 오차")

3. 학습 비용¶
hourly는 같은 기간이라도 타임스텝 수가 24배입니다 (9년 학습 기간 = 약 78,000 스텝). 게다가 seq_length를 365 → 720으로 늘렸으므로 한 샘플의 길이도 2배가 되었습니다. 즉 한 epoch의 연산량은 daily의 대략 40배 수준입니다. CudaLSTM처럼 cuDNN이 시퀀스를 통째로 처리하는 모델은 그래도 epoch당 수십 초면 끝나지만, 타임스텝마다 파이썬 루프를 도는 모델들(ARLSTM, CustomLSTM, EA-LSTM, MC-LSTM, HybridModel)은 epoch당 수 분이 걸립니다.
